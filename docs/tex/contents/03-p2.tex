\section{Rancangan Solusi}

Sistem memisahkan pengambilan data sumber dari pelayanan permintaan pengguna.
Aggregator menjalankan poller BMKG dan PVMBG sebagai dua goroutine independen,
sementara layanan gRPC membaca data kanonis di PostgreSQL. Publisher outbox
berjalan pada goroutine lain. Pemisahan ini terlihat pada
\code{services/aggregator/cmd/main.go}. Dengan demikian, keterlambatan PVMBG
memengaruhi waktu pembaruan data PVMBG, bukan menambahkan waktu tunggu upstream
ke setiap pembacaan BMKG. Permintaan pengguna tetap bergantung pada kapasitas
gateway, autentikasi, Aggregator, dan database yang dipakai bersama.

Setiap poller melakukan pengambilan awal, kemudian mengulangi polling menurut
interval masing-masing. HTTP client memiliki timeout per sumber dan menerima
context untuk pembatalan saat layanan berhenti. Dalam satu poller, satu putaran
diselesaikan sebelum putaran berikutnya diproses; implementasi tidak membuat
goroutine baru tanpa batas pada setiap tick. BMKG mengambil seismic event lalu
peringatan tsunami secara berurutan, sedangkan PVMBG mengambil laporan vulkanik.
Implementasi berada pada \code{services/aggregator/internal/ingest/bmkg.go} dan
\code{services/aggregator/internal/ingest/pvmbg.go}.

Setiap sumber mempunyai watermark, waktu keberhasilan terakhir, waktu percobaan
terakhir, dan pesan kegagalan. Setelah fetch berhasil, data dinormalisasi dan
disimpan sebelum watermark dimajukan. Pada kegagalan, data sebelumnya tidak
dihapus dan watermark keberhasilan dipertahankan. Pada pembacaan API,
\code{services/aggregator/internal/domain/status.go} menghitung status berikut:
\begin{itemize}
    \item \textbf{FRESH}: keberhasilan terakhir masih dalam ambang waktu dan
    tidak ada error sumber yang tercatat.
    \item \textbf{STALE}: sumber gagal atau terlalu lama tidak berhasil,
    tetapi data kanonis sumber tersebut masih tersedia.
    \item \textbf{UNAVAILABLE}: tidak tersedia data tersimpan untuk digunakan
    ketika sumber belum berhasil atau tidak dapat diperbarui.
\end{itemize}

Respons hazard tetap membawa item yang tersedia beserta metadata
\code{freshness}. Nilai \code{partial=true} diberikan apabila sumber yang
relevan dengan permintaan tidak fresh. Filter sumber membatasi pemeriksaan
kesegaran pada sumber tersebut. Mekanisme ini membedakan kondisi tidak ada
peristiwa dari sumber yang belum dapat memberikan data, sekaligus memungkinkan
klien menampilkan usia data. Pembentukan respons ada pada
\code{services/aggregator/internal/grpc/server.go}; penyimpanan watermark ada
pada \code{services/aggregator/internal/store/hazard_store.go}.

Gateway juga membatasi permintaan unary aktif dengan channel berkapasitas
tetap. Ketika penuh, permintaan ditolak dengan respons overload sesuai kontrak,
umumnya HTTP 429, dan \code{Retry-After}. Deadline unary membatasi waktu tunggu
backend. Pembatas ini bukan pembatas laju per pengguna dan tidak menghitung
stream SSE yang berumur panjang. Kode terkait adalah
\code{services/api-gateway/internal/server/server.go},
\code{services/api-gateway/internal/config/config.go}, dan
\code{services/api-gateway/internal/problem/problem.go}.

\section{Justifikasi dan Alternatif}

Polling independen dipilih karena data kebencanaan dikumpulkan secara berkala
dan dapat dilayani dari penyimpanan kanonis. Pengguna memperoleh respons dari
satu bentuk data meskipun kedua sumber memiliki latensi serta skema berbeda.
Biaya keputusan ini adalah jeda antara perubahan upstream dan kemunculannya
pada API. Karena itu, freshness merupakan bagian dari kontrak respons, bukan
sekadar informasi log.

Alternatif pertama ialah melakukan dua panggilan upstream secara serial pada
setiap request. Pendekatan tersebut sederhana, tetapi latensi sumber terakumulasi
dan gangguan satu sumber langsung memengaruhi request pengguna. Alternatif kedua
ialah fan-out paralel per request dengan deadline terpisah. Pendekatan kedua
mengurangi penjumlahan waktu tunggu, tetapi tetap menambah beban upstream
sebanding dengan jumlah pengguna dan memerlukan fallback tersendiri.

Penyimpanan kanonis dengan polling mengurangi keterikatan tersebut, dengan
konsekuensi kapasitas database menjadi sumber daya bersama. Pool koneksi dan
batas unary gateway menahan pertumbuhan pekerjaan aktif. Penggunaan circuit
breaker atau penjadwal polling terdistribusi dapat menjadi pengembangan
berikutnya, tetapi keduanya belum menjadi mekanisme yang digunakan pada
implementasi ini.

\section{Batasan Solusi}

Isolasi pada tingkat goroutine tidak menjamin isolasi CPU, memori, database,
atau autentikasi. Permintaan BMKG dan PVMBG tetap melewati komponen bersama.
Kegagalan PostgreSQL tidak dapat ditutupi oleh fallback memori karena jalur
baca kanonis masih membutuhkan database. Compose juga belum memberikan bukti
failover beberapa replika Aggregator atau database.

Pembaruan watermark dilakukan sesudah transaksi data selesai, bukan di dalam
transaksi yang sama. Restart pada sela kedua operasi dapat menyebabkan data
diambil kembali; kestabilan identitas hazard menjaga baris kanonis tetap satu
per referensi sumber.

Nilai timeout, kapasitas pool, serta semaphore merupakan konfigurasi atau
mekanisme yang digunakan pada kode. Hasil beban yang dilampirkan di bawah
mengukur satu lingkungan lokal dan satu jendela pengujian; hasil tersebut
tidak merupakan jaminan kapasitas produksi atau availability jangka panjang.
Skenario outage membuktikan degradasi dan pemulihan pada demonstrasi yang
dicatat, bukan failover infrastruktur.

\subsection{Tooling dan Konfigurasi Load Testing}

Pengujian beban menggunakan \textbf{Grafana k6}~\cite{k6}. k6 dipilih karena
skenario ditulis sebagai skrip JavaScript yang tersimpan di repositori, mendukung
beberapa \emph{scenario} dengan executor dan jadwal mulai berbeda dalam satu run,
serta dapat memberi tag pada setiap request sehingga persentil dapat dihitung per
fase dan per endpoint. Dua skrip digunakan:
\code{tests/load/aggregator.js} untuk beban berkelanjutan dan
\code{tests/load/aggregator-isolation.js} untuk isolasi latensi; fungsi bersama
(token, request, validasi, ringkasan) berada pada \code{tests/load/lib.js}.
Petunjuk menjalankan tersedia pada \code{docs/load-testing.md}.

\paragraph{Jalur yang diuji.} k6 tidak memanggil Aggregator secara langsung.
Setiap request dikirim ke Envoy pada \code{http://127.0.0.1:8080} dengan header
\code{Host: localhost:8080}, sehingga melewati jalur yang sama dengan klien:
Envoy $\rightarrow$ \code{ext_authz} Token Exchange Sidecar $\rightarrow$
API Gateway $\rightarrow$ gRPC Aggregator $\rightarrow$ PostgreSQL. Identitas yang
dipakai adalah akun service \code{svc-bnpb} (role BNPB\_INTERNAL); secret-nya dibaca
dari \code{.cache/auth/}.

\paragraph{Alur setiap Virtual User (VU).}
\begin{enumerate}
    \item \textbf{Setup (sekali per run).} Skrip meminta token lalu memanggil
    \code{GET /api/v1/hazards?page_size=100} sampai daftar tidak kosong, kemudian
    menyimpan hingga 100 \code{hazard_id} untuk request detail. Request setup diberi
    tag tersendiri dan tidak dihitung dalam hasil.
    \item \textbf{Token per VU.} Setiap VU meminta access token sendiri melalui
    \code{POST /oauth/v2/token} (grant \code{client_credentials}, Host
    \code{auth.localhost:8080}) dan menyimpannya di memori VU. Token diperbarui
    10 detik sebelum TTL 60 detik berakhir, sehingga selama 60 detik fase beban
    tiap VU melakukan sekitar satu sampai dua kali penerbitan token. Request token
    diberi tag \code{kind:token} dan dikeluarkan dari persentil API; kegagalannya
    dihitung pada metrik \code{token_failures}.
    \item \textbf{Iterasi.} Setiap iterasi mengirim tepat satu request API dengan
    header \code{Authorization: Bearer} dan \code{X-Correlation-ID} unik
    (\code{runId-vu-iterasi}) untuk pencocokan trace. Tidak ada \emph{think time};
    VU langsung memulai iterasi berikutnya setelah respons diterima (model
    \emph{closed-loop}), sehingga 50 VU berarti paling banyak 50 request API
    bersamaan.
    \item \textbf{Validasi respons.} Request dianggap error bila status bukan 200
    atau bentuk body tidak sesuai: daftar wajib memiliki array \code{items},
    detail wajib memiliki \code{item.hazard_id}, status sumber wajib memiliki
    array \code{freshness}. Jumlah per status HTTP (termasuk 429 dan error
    jaringan) dicatat terpisah.
\end{enumerate}

Grup kedua pada skrip isolasi sengaja menjaga total VU tetap 20 pada kedua fase;
satu-satunya perbedaan baseline dan kontensi adalah jenis lalu lintas grup kedua
(BMKG $\rightarrow$ PVMBG). Threshold yang menentukan lulus/gagal adalah
\code{p(95)<300} ms dan error di bawah 1\% pada request BMKG fase kontensi;
pada skrip beban, error API di bawah 1\% dan tidak ada kegagalan token.

Prosedur pengulangan:
\begin{enumerate}
    \item Jalankan stack yang telah diprovisikan, pastikan akun layanan tersedia
    pada \code{.cache/auth/}, dan buat direktori \code{.cache/load/}.
    Jalankan \code{k6 run tests/load/aggregator.js} dari root repositori.
    Parameter dapat diubah melalui \code{LOAD_VUS}, \code{LOAD_DURATION}, dan
    \code{LOAD_RAMP}.
    \item Untuk isolasi, tetapkan
    \code{PVMBG_RESPONSE_DELAY_MIN_MS} dan
    \code{PVMBG_RESPONSE_DELAY_MAX_MS} menjadi 3000, lalu buat ulang
    \code{pvmbg-mock} sebagaimana panduan. Jalankan
    \code{k6 run tests/load/aggregator-isolation.js}. Setup mengirim tiga
    request langsung ke \code{/volcanic-reports} pada mock (port 8082) dan
    membatalkan pengujian bila median delay kurang dari 2900 ms.
    \item Simpan keluaran terminal dan ringkasan JSON yang ditulis skrip ke
    \code{.cache/load/}. Ringkasan isolasi mencantumkan jendela waktu baseline
    dan kontensi untuk pencocokan trace. Pulihkan konfigurasi delay setelah
    selesai.
\end{enumerate}

Latensi yang diukur skrip tersebut mencakup Envoy, token exchange, gateway,
RPC, dan pembacaan database. Angka yang dilaporkan merupakan latensi jalur API
lengkap, bukan waktu eksekusi Aggregator saja. Hasil k6 beban tersimpan pada
\code{evidence/P2/aggregator-2026-10-09T15-31-17-502Z.json}; hasil k6 isolasi tersimpan
pada \code{evidence/P2/aggregator-isolation-2026-10-09T15-37-25-357Z.json},
relatif terhadap direktori laporan. Tangkapan layar pada direktori \code{evidence/P2/} memperlihatkan
konfigurasi, fase, hasil, dan nama ringkasan JSON yang bersesuaian.

Untuk menilai batas error spesifikasi, HTTP 429 yang merupakan backpressure
terkendali dilaporkan terpisah dari error tidak terkendali. Pada fase beban,
catat jumlah request API $N$, jumlah 429 $N_{429}$, dan kegagalan lain
$N_{\mathrm{err}}$; laporkan $100N_{\mathrm{err}}/N$ serta
$100N_{429}/N$. Denominator dan definisi kegagalan harus dicantumkan agar
angka dapat diperiksa. Threshold error bawaan skrip masih menghitung 429,
sehingga lebih ketat daripada penghitungan penerimaan yang mengecualikannya.
Hasil token endpoint tidak dicampur ke persentil request API.

\subsection{Outage, Data Stale, dan Pemulihan}

\code{evidence/P2/3-5.png}. Outage PVMBG diaktifkan melalui kontrol admin,

sumber tidak ditampilkan sebagai tidak adanya kejadian. Setelah outage

Ringkasan pengujian otomatis, \code{evidence/problem_set_report.md}, mencatat tiga
tes P2 berhasil dalam 74,97 detik. Tes outage pada
\code{tests/test_problem_2.py} memeriksa data PVMBG tersimpan tetap tersedia,
HTTP 200, status stale, serta pemulihan ke fresh setelah outage dinonaktifkan;
prosedur tes tersebut tidak menjalankan restart. Namun, gambar manual tidak
melampirkan identitas dan waktu mulai container sebelum/sesudah, sehingga
gambar saja tidak membuktikan tidak terjadi restart di luar prosedur.

Narasi kriteria pada ringkasan pengujian otomatis merupakan template ringkasan, bukan rekaman angka
latensi atau konfigurasi efektif. Pengukuran 50 VU/60 detik dan validasi delay
PVMBG karena itu dirujukkan ke JSON k6 beban dan isolasi. Bukti ini mendukung skenario yang
terekam, tanpa mengklaim ketahanan outage berkepanjangan atau availability
di luar jendela pengujian.
