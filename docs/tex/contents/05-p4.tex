\chapter{P4: Layanan dan Penyimpanan}
\label{chap:p4}

\section{Rancangan Solusi}

Pemisahan layanan mengikuti tanggung jawab pengolahan data dan cara
penyampaiannya. Aggregator mengintegrasikan sumber eksternal ke model kanonis;
Event Live Feed melayani aliran event; Webhook Provider mengirim callback;
Danger Notification memilih peringatan untuk push notification. Gateway
menerjemahkan kontrak HTTP menjadi panggilan gRPC, sehingga layanan domain
tidak perlu mengimplementasikan ulang seluruh antarmuka publik.

Consumer telah diimplementasikan dalam tiga bahasa: Rust untuk Event Live Feed,
Go untuk Webhook Provider, dan C\# untuk Danger Notification. Kontrak Protobuf
menjadi batas pertukaran data lintas bahasa. Compose membangun masing-masing
image dari direktori layanannya dan menghubungkannya melalui jaringan Docker.
Pemisahan proses memungkinkan restart satu consumer tanpa harus mematikan
consumer lain, meskipun kemandirian operasional tetap dibatasi dependency yang
dipakai bersama.

Aggregator memiliki tabel \code{hazard_events} dengan kunci
\code{hazard_id} dan batas unik pasangan \code{source} serta
\code{source_ref_id}. Atribut umum disimpan sebagai kolom bertipe, sedangkan
atribut yang berbeda menurut sumber disimpan dalam JSONB. Kombinasi ini
memungkinkan filter lintas sumber tanpa membuang informasi khusus sumber.
Tabel \code{ingest_watermarks} menyimpan kemajuan ingestion dan kesegaran,
\code{outbox_events} menyimpan publication yang belum dikirim, dan
\code{outbox_dead_letters} menyimpan publication yang mencapai batas gagal.
Schema yang diterapkan saat startup berada pada
\code{services/aggregator/internal/store/postgres.go}.

Kepemilikan logis Canonical Store berada pada Aggregator. Danger Notification
menerima snapshot hazard dari event broker dan menyimpannya pada SQLite
melalui \code{EfNotificationStore}. Daftar dan detail notifikasi dibaca dari
penyimpanan lokal ini, sedangkan status kesegaran sumber tetap diperoleh
melalui adapter gRPC Aggregator. FCM mengelola subscription token ke topic.
Dengan demikian, data notifikasi tidak memerlukan query langsung ke tabel
hazard milik Aggregator.

Tabel \code{notifications} memakai ID publication sebagai primary key dan
menyimpan snapshot Protobuf hazard, \code{hazard_id}, waktu publication,
penanda \code{IsCurrent}, status push, jumlah kegagalan, jadwal retry, dan
lease pekerjaan. Revisi baru menandai revisi lama hazard yang sama sebagai
tidak current; API daftar/detail menampilkan revisi current. Upsert dan
pembaruan revisi menggunakan transaksi SQLite. \code{PushOutboxWorker}
mengambil pekerjaan yang waktunya sudah tiba, mengirim melalui FCM, lalu
mencatat hasilnya. Compose memasang \code{notification_data} pada
\code{/data}, dengan database \code{notifications.db}. Registrasi layanan
dan migrasi berada pada \code{Program.cs} serta adapter
\code{Adapters/Outbound/Persistence/} di layanan Danger Notification.

Webhook Provider memiliki database SQLite tersendiri untuk
\code{webhook_subscriptions}, \code{webhook_deliveries}, dan
\code{delivery_dedup}. Mode WAL digunakan dan pool dibatasi satu koneksi
terbuka. Kunci gabungan \code{event_id} dan \code{webhook_id} pada tabel
dedup menandai delivery yang berhasil. Implementasi berada pada
\code{services/webhook-provider/internal/store/sqlite.go}.
Compose memasang volume \code{webhook_data} pada \code{/data}; DSN contoh
mengarahkan database ke \code{file:/data/webhook.db}.

Event Live Feed menggunakan abstraksi \code{ReplayStore} dengan implementasi
\code{MemoryStore}. Buffer menyimpan urutan event dan himpunan ID yang sudah
diterima, dilindungi mutex, lalu menyebarkan event ke kanal broadcast.
Default Compose membatasi replay pada 600 detik atau 10.000 entri, sedangkan
kanal live memiliki kapasitas 256 entri. Ketika subscriber tertinggal, backlog
dapat dibaca kembali selama belum keluar dari jendela replay. Restart
membentuk epoch baru dan cursor lama ditolak, sehingga klien mengetahui bahwa
riwayat sebelumnya tidak lagi tersedia. Sumbernya adalah
\code{services/event-live-feed/src/core/ports.rs} dan
\code{services/event-live-feed/src/adapters/outbound/memory_store.rs}.

\section{Justifikasi dan Alternatif}

Pemilihan penyimpanan mengikuti kebutuhan masing-masing layanan. PostgreSQL
memberikan transaksi untuk menyimpan hazard dan outbox bersama, keunikan
identitas sumber, serta indeks untuk penyaringan dan paginasi. SQLite
memadai untuk volume subscription dan log webhook pada satu instance,
dengan biaya operasi rendah. Memori proses menyediakan replay live-feed yang
ringan ketika kontraknya memang membatasi umur riwayat.

\begin{table}[htbp]
    \centering
    \small
    \caption{Alternatif penyimpanan dan pertimbangannya}
    \begin{tabularx}{\textwidth}{@{}P{0.19\textwidth}X X@{}}
        \toprule
        \textbf{Pilihan} & \textbf{Kelebihan untuk kasus ini} & \textbf{Biaya atau batasan} \\
        \midrule
        PostgreSQL, dipakai Aggregator & Transaksi hazard--outbox, constraint identitas, dan kolom JSONB untuk atribut sumber. & Memerlukan proses database dan pengelolaan koneksi; kapasitasnya dipakai seluruh pembacaan kanonis. \\
        SQLite, dipakai webhook & Penyimpanan lokal persisten tanpa server database tambahan; schema dan dedup mudah diperiksa. & Satu penulis dan satu volume lokal membatasi replikasi horizontal. \\
        MongoDB, alternatif & Dokumen fleksibel untuk payload sumber yang beragam. & Perlu merancang kembali indeks gabungan, transaksi publication, dan kontrak query; fleksibilitas payload sudah dapat ditampung JSONB. \\
        Redis, alternatif replay & Data replay dan dedup dapat ditempatkan di luar proses feed untuk dipakai beberapa instance. & Menambah dependency; TTL, eviction, persistensi, dan posisi cursor perlu dirancang eksplisit. \\
        \bottomrule
    \end{tabularx}
\end{table}

Alternatif satu database bersama untuk semua layanan mengurangi jumlah
komponen, tetapi memungkinkan perubahan schema satu layanan memengaruhi
layanan lain secara langsung. Rancangan yang dipilih membatasi akses melalui
kontrak gRPC atau event. Fleksibilitas penyimpanan berarti implementasi
penyimpanan dapat disesuaikan per kebutuhan; bukan berarti mengganti database
tanpa migrasi data, perubahan adapter, dan pengujian ulang.

Untuk feed, penyimpanan eksternal seperti Redis atau PostgreSQL dapat
memperpanjang replay lintas restart. Implementasi saat ini memilih memori,
sehingga biaya serialisasi dan I/O penyimpanan lebih kecil, tetapi tidak
mengklaim riwayat permanen. Untuk webhook berskala lebih besar, PostgreSQL
dapat menggantikan SQLite agar beberapa worker mempunyai state dedup
bersama, dengan tambahan koordinasi pekerjaan dan pengendalian duplikasi.

\section{Batasan Solusi}

Pemisahan image dan proses belum membuktikan bahwa setiap layanan dapat
direplikasi tanpa perubahan. Publisher outbox belum memakai mekanisme
claim/lock antar-worker pada query pengambilan record. Feed memiliki replay
dan epoch lokal per proses. SQLite webhook membatasi penulisan serta
memerlukan strategi berbagi state sebelum menjalankan beberapa replica.
Keterbatasan ini perlu diselesaikan sebelum menyatakan dukungan penskalaan
horizontal yang transparan.

Durability harus dibedakan per komponen. PostgreSQL menggunakan volume
\code{aggregator_data}; SQLite menggunakan \code{webhook_data} dan
\code{notification_data} untuk masing-masing layanan.
Data tersebut tetap bergantung pada lifecycle volume dan prosedur backup.
Feed tidak persisten setelah restart. Notification menyimpan status push
dan identitas publication secara lokal; status diterima FCM belum merupakan
bukti pesan telah tampil pada perangkat pengguna. RabbitMQ mendeklarasikan queue durable, tetapi
\code{compose.yaml} belum memasang volume data broker secara eksplisit.
Karena itu, ketahanan seluruh state setelah container dibuat ulang belum
menjadi jaminan sistem.

Penyimpanan hazard mempertahankan satu identitas kanonis per referensi
sumber, tetapi upsert tidak membandingkan seluruh isi untuk memastikan
perubahan substantif. Publication baru tetap dapat dibentuk untuk data
yang diambil ulang. Pemisahan database dan penggunaan constraint tidak
dengan sendirinya menyediakan pemrosesan event tepat satu kali.

\subsection{Kepemilikan Data dan Batas Pengujian}

M4 \code{P4/3.png} memperlihatkan inspeksi konfigurasi serta keberhasilan
pembacaan status sumber melalui API. Pada kode aplikasi, operasi Canonical
Store ditangani Aggregator; consumer memperoleh data lewat event atau API.
Pemeriksaan otomatis mencari variabel \code{CANONICAL_STORE_DSN} secara
literal dalam blok Compose layanan lain. Pemeriksaan ini menunjukkan
konvensi konfigurasi yang diperiksa, tetapi tidak membuktikan pembatasan
akses database pada tingkat jaringan atau hak pengguna.

Konfigurasi saat ini masih memuat \code{env_file: .env} pada Webhook
Provider, sehingga variabel Canonical Store dalam berkas tersebut ikut
masuk ke lingkungan container. Database juga berada pada jaringan bersama
dan port PostgreSQL diekspos ke host; collector observabilitas mempunyai
koneksi PostgreSQL untuk metrik. Dengan demikian, istilah kepemilikan
pada laporan ini berarti pemisahan tanggung jawab aplikasi. Pembatasan
credential per layanan, role metrik khusus, dan jaringan database perlu
diterapkan bila kriteria akses eksklusif hendak dijamin secara teknis.
